# Data Detective 学习笔记

这个项目新增的能力是：把「发现疑点」变成一条可检查、可试改、可保存、可恢复的用户操作路径。已有的评测、模型调用和服务经验，在这里需要落实到具体记录与用户决策。

## 第二轮优化：从小样例跑通到完整数据可用

第一版只展示前 40 条线索、前 500 行，导致后面的数据虽然被检查了，用户却无法方便地处理。现在搜索覆盖全表，线索、证据和改动分页显示；修复可以输入 `27, 31, 501-505` 这样的原始行号。分页限制的是一次显示多少，不是业务上能处理多少。

Streamlit 默认会运行所有标签页，包括没打开的导出页。因此仅仅改一个输入，也可能重新生成多份 CSV 和报告。现在只执行当前标签页，用户点击准备导出时才生成文件，再按保存版本复用。核心检查很快，不代表整条交互路径就快，优化应先找重复工作。

草稿和保存版本是不同的状态：切换案件保留本次会话的草稿，确认保存才生成磁盘快照。恢复确认必须绑定目标版本和原因，不能让用户勾选 A 后切换 B，仍用旧的勾选确认 B。预览和保存之间还要复制可变的行选择与设置，避免调用者事后修改审计内容。

AI 优化保留严格校验，先减少输入里容易被模型复述的原始金额与日期，再缓存同一问题和证据下的已验证结果。三个旧题重测通过只是排查改动是否有效，不应写成「准确率 100%」。[完整优化记录](OPTIMIZATION.md) 保留了这些结论的范围。

## 先把计算口径讲清楚

用户上传的是字符串，不是已经可靠的业务事实。先让用户确认订单、商品、数量、单价、时间的列映射，再确认日期格式、小数点、千分位和币种。`01/02/2011` 无法仅凭字符串判断是二月一日还是一月二日，程序不替用户猜。

核心检查使用 Python 和 `Decimal`；pandas 仅用于界面表格。金额按有符号数量 × 单价求和，结果叫「净交易金额」，不能自动等同会计收入。退货已经用负数量表达时，不再因为订单号以 C 开头就再取一次负号。

例如三条记录中，一条单价是 `two`，它不能进入金额合计，界面必须同时显示未能计算的行数。另一条金额有效、日期无效，它仍进入总额，但进入「月份未分配金额」，而不是悄悄消失。

## 检查不是自动判错

检查输出 `Finding`：规则、严重程度、受影响行、字段、证据和解释。缺值与无法解析是 `error`；整行完全相同和商品价格离群是 `review`。同一个订单买多种商品很正常，订单号重复不能作为去重依据。

案例中特意放入两条合法但完全相同的销售记录。只看 CSV，系统无法知道这是重复导入，还是两次真实事件。因此它应该提示检查，不应该自动删掉其中一条。价格离群也一样：促销、商品规格变化和真实错误都可能造成异常，三倍 IQR 只提供线索。

真实 UCI 原始数据本身也有疑点，所以 `baseline.csv` 只是修改前的参照，不是「绝对干净的答案」。先记录 baseline 检查，再检查注入后的 input，才能区分新引入的错误和原本就存在的疑点。

## 修复预览为什么值得单独实现

修复计划明确记录：基于哪个版本、对哪些行、改哪个值、为什么改。支持指定值替换、排除行、去掉首尾空格和修改解析设置。排除行只改变是否参与计算的标记，原始记录仍保留。

多个操作必须组合起来重新计算，不能把单步影响简单相加。例如先修日期再排除同一行，最终月度金额不能把这行计算两次。预览返回完整的前后指标、精确差额和逐格变更，并且不写入磁盘。

用户确认时，系统重新检查预览指纹与当前版本。另一操作已经改过数据，就必须重新预览。幂等键解决重复点击：同一个动作只保存一次，相同键带着不同内容则被拒绝。恢复历史版本也生成新版本，让「修过又恢复」本身留在历史里。

## 几个应当主动演示的失败场景

| 场景 | 应观察到什么 |
|---|---|
| 日期格式错误 | 具体原始值可见；有效金额仍在总额中，月份覆盖不足被显示。 |
| 预览之后当前版本改变 | 保存被拒绝，要求重新预览。 |
| 重复提交同一保存动作 | 返回同一已保存版本，不增加第二次修复。 |
| 手动改坏已保存快照 | 读取校验失败，不把变动当成可信历史。 |
| Qwen 路径不存在、超时或回答格式不合格 | 显示回退原因，规则引导仍可用。 |
| 所有检查都通过 | 只说明这些已实现的检查没发现问题，不表示业务数据完全正确。 |

## 模型该负责哪一小部分

模型只根据已经计算出的线索，建议先看哪里和下一步验证什么。它不算权威金额、不生成可执行修复代码，也不直接保存变更。结构化输出及引用校验能阻止一部分错误，但不能证明自由文本完全正确。

模型放在一次性独立进程中运行，超时后结束，避免拖住主应用。代价是每次调用重新加载模型，冷启动时间必须计入延迟。已有 GPU 环境可以通过 `DATA_DETECTIVE_MODEL_PYTHON` 复用；缺少 GPU 或模型权重时，完整规则流程仍然可运行。

## 怎样诚实地证明项目能力

十二个冻结案例使用互不重叠的真实源行，另有明确标注的合成控制。案例记录注入前后单元格和恢复答案，不读取检测器来决定标签。评测里把检测器替换成「没有发现任何问题」后，检出率必须下降；这能防止把实现本身当作标准答案。

已知注入被发现，证明对应规则在这批案例上工作；按 oracle 恢复 baseline，证明修复机制正确。它们都不证明系统可以自主判断真实业务意图。合法重复的 review 也不能混算成 error 误报，二者必须分开报告。

面试演示可以讲三件具体的事：为什么合法退货没有被误删，为什么日期错误会造成总额和月度图不一致，以及为什么一次看似简单的保存也需要版本检查、指纹和幂等键。真实试用的完成时间与理解程度仍需另做研究；脚本测试不是用户研究。
